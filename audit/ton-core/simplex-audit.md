# TON Core — Simplex Consensus Message Handling — Bug Bounty Audit

**Date:** 2026-11-11 (WIB)
**Program:** TON Security Bug Bounty (README at `~/workspace/ton-bug-bounty/README.md`; self-check skill at `~/workspace/ton-bug-bounty/skills/bug-bounty-self-check.md`)
**Method:** Read-only static analysis. No exploit traffic, no state-changing tests against public mainnet/testnet nodes, public RPC/lite servers, or any live network. No submission was made and the bounty bot was not contacted.
**Scope bar applied:** CRITICAL only — a **single remote consensus message** (proposal, vote, certificate, candidate, state) from an **unprivileged** sender that halts a validator/node or manipulates blockchain state/funds. Validator-initiated attacks, quorum/majority attacks, OOM/DDoS/resource exhaustion, MisbehaviorProof absence, and all other README exclusions were treated as non-qualifying.

## Verdict: NO QUALIFYING FINDING

No candidate was found that plausibly meets the program's critical bar. Every remote consensus message path traced is gated on one of: (a) membership in the private consensus overlay (validators, delegated collators, and — only if configured — observers), (b) an Ed25519 signature by the expected leader/validator over the session-bound payload, or (c) a 2/3-weight quorum of validator signatures. The remaining CHECK-fail paths all require a faulty quorum (explicitly excluded: fail-stop under a faulty quorum is intentional), a local operator action, or a local timing condition — none is triggerable by a single message from an unprivileged remote peer. **Submit nothing from this audit.**

## Threat model established (who can send what)

This is the decisive filter for the whole audit, and it was verified in code rather than assumed:

- **Transport gate.** All Simplex protocol messages arrive via the **private** consensus overlay (`private-overlay.cpp`, `block-sync-overlay.cpp`), created with `OverlayPrivacyRules{0, 0, authorized_keys}` over exactly the validator set (+ collators on non-masterchain shards, + all overlay nodes only if `observers_in_private_overlay()` is configured). Unicast delivery checks `check_src_peer` (`overlay/overlay.cpp:372-382`); non-members are dropped before any consensus handler runs. An arbitrary remote ADNL node **cannot** deliver a vote, certificate, candidate, or request to `Pool`/`CandidateResolver`/`CollatorProducer`.
- **Votes.** `PoolImpl` (`pool.cpp`, `IncomingProtocolMessage` handler) drops any vote whose ADNL source is not a validator (`source_validator` is derived from the overlay's ADNL→validator map, not from message bytes), then verifies the Ed25519 signature over the session-bound vote (`Signed<Vote>::from_tl`, `votes.cpp:74-88`) before the vote is counted. A validator can only ever vote as itself. A bad signature bans the sender's ADNL id for `bad_signature_ban_duration` — a local, bounded penalty, not a halt.
- **Certificates.** The certificate path does **not** check the sender at all — but it does not need to: `Certificate<T>::from_tl` (`certificate.cpp:24-58`) verifies every listed signature against the named validator's key and requires total weight `>= (total_weight * 2) / 3 + 1`. A certificate is self-authenticating; forging one requires quorum keys. Any defect reachable only through a valid certificate is therefore a quorum-attack defect, excluded.
- **Candidates.** Broadcast candidates are verified against the expected leader for the slot and the leader's (or delegated collator's) session-bound signature (`Candidate::deserialize_data`, `types.cpp`), with payload size caps (`max_block_size` / `max_collated_data_size`) enforced before the signature check. Candidate requests/responses are validated the same way (`CandidateAndCert::from_tl`, `candidate-resolver.cpp:38-63`).
- **Collator requests.** `pleaseCollate`/`pleaseCollatePrepare` are accepted only from a validator (`source_validator` required), only from the expected leader of the window, and only with a valid delegation signature plus collator-whitelist checks (`collator-producer.cpp`).

## Most interesting non-qualifying observations (NOT reportable — do not submit)

### 1. Honest-validator self-equivocation race: SkipVote + NotarizeVote for the same slot — STILL PRESENT, but not a qualifying finding (confidence in mechanism ~85, fit ~10)

**Code (current commit `857b8a5`):**
- `consensus.cpp`, `alarm()`: skips every non-final slot in the window — guard is only `!slot->state->voted_final`. It does **not** check `voted_notar`/`voted_skip`, and it does not check whether a candidate for the slot is currently being validated.
- `consensus.cpp`, `try_notarize()`: an async coroutine that suspends at `WaitForParent`, `ResolveState`, and `ValidationRequest` before setting `voted_notar` and broadcasting `NotarizeVote`. It never re-checks `voted_skip` after those suspension points.
- `consensus.cpp`, `start_up()`: after restoring `voted_notar` from the DB bootstrap votes, the `first_nonannounced_window` loop broadcasts `SkipVote` for every non-final slot — again guarded only by `!voted_final`, so a validator that restarts after voting notar (but before finalization) deterministically broadcasts a conflicting `SkipVote` for the same slot.
- `pool.cpp`, `Tsentrizbirkom::check_invariants()`: flags notarize≠finalize and finalize+skip as conflicting, but **not** notarize+skip — so peers silently accept both votes from the same validator (no `MisbehaviorReport`).

**Mechanism:** if block validation is slower than the alarm interval (heavy blocks, high load, slow hardware), the alarm fires mid-validation: the validator broadcasts `SkipVote{s}`, sets `voted_skip`, then validation completes and it broadcasts `NotarizeVote{s}` anyway. Its `voted_skip` then blocks its own `try_vote_final`, so the slot is skipped instead of finalized and the candidate block is abandoned. If validation is slow on many validators at once, many slots are skipped and throughput degrades.

**Why NOT reportable under this program (three independent reasons):**
- **No single remote trigger.** The trigger is local timing (validation latency vs. the alarm) or the operator's own restart — not a consensus message from an unprivileged peer. No attacker message can force a victim's validation to be slow; the only party that can inflate validation time is the leader that collated a heavy block, i.e. a validator (validator-initiated, excluded).
- **Impact is degradation, not a halt.** Both a `NotarCert` and a `SkipCert` can form for the same slot, but the pool handles that combination without crashing (no CHECK on it), `advance_present` moves past the skipped slot, and later windows proceed on the available base. The worst demonstrated effect in the prior audit's own test was severe throughput degradation with candidate blocks abandoned — not a node halt and not a demonstrated persistent network halt (the skip back-off grows `first_block_timeout_` by a multiplier up to a cap after skip windows, so the race self-limits as timeouts lengthen).
- **Already publicly reported (duplicate risk).** This exact race — bugs A/B/C above, including the restart variant — was published 2026-03-14 by Tesserae Ventures ("TON Simplex Consensus — Security Findings", findings 1–2, testnet commit `3bb6abc`, submitted for Blockchain Contest Round 2) with a `test-consensus` reproduction. It is therefore very likely already known to the TON team; a resubmission would almost certainly be a duplicate even if it were otherwise eligible.

### 2. `FinalCert` handler CHECKs assume Final–Skip exclusion — requires a faulty quorum (excluded)

`pool.cpp`, `handle_typed_saved_certificate(FinalCertRef)`: `CHECK(!slot.state->is_skipped())` and `CHECK(slot.state->notarized_block().value_or(id) == id)`. A `FinalCert` for an already-skipped slot would abort the node. But a `FinalCert` needs 2/3 finalize-vote weight, and honest validators cannot vote both skip and final for a slot: `try_vote_final` refuses when `voted_skip` is set, and `alarm()` refuses to skip a slot with `voted_final`. Forming both a `SkipCert` and a `FinalCert` for one slot therefore needs ≥1/3 of weight to sign contradictory votes — a faulty quorum. Per the README, CHECK failures under a faulty quorum are intentional fail-stop behavior, not a bounty issue. (The notarize+skip equivocation of observation 1 does **not** open this path, because equivocating validators have `voted_skip = true` and are exactly the ones barred from voting final.)

### 3. `Proven::as_signed_vote()` CHECK relies on a `being_saved` invariant — analyzed, not reachable

`pool.cpp`: `SlotState::create_cert` calls `Tsentrizbirkom::to_signature`, which calls `Proven::as_signed_vote()` — `CHECK(std::holds_alternative<Signed<T>>(proof))`. A vote stored from a certificate (proof = `CertificateRef`) would trip this CHECK if `create_cert` ever iterated it. It cannot in the current code: `create_cert` is only called from `handle_typed_vote`, which is gated on `!slot.state->will_be_notarized()`, and `will_be_notarized()` is true from the moment `handle_certificate` sets `being_saved` (synchronously, in the same serialized actor turn, before the async `SaveCertificate`) until the certificate is stored. Certificate-proven votes are added only inside `handle_prospective_certificate`, which is only reached via `handle_certificate`. The invariant is subtle and flag-based rather than type-enforced (a future refactor that adds a certificate-proven vote without setting `being_saved` would turn this into a remote-triggerable crash — the trigger certificate itself is quorum-signed, so even then it would sit in the excluded quorum class), but as written there is no reachable path. Defense-in-depth note only.

### 4. `.move_as_ok()` on broadcast-extra parsing — gated by the overlay precheck

`private-overlay.cpp` and `block-sync-overlay.cpp`, `on_overlay_broadcast`: `parse_broadcast_extra(extra).move_as_ok()` would abort on malformed `extra`. This is **not** reachable with malformed bytes: the overlay's two-step broadcast path calls `precheck_broadcast` (with `signature_checked=false` and then `=true`) **before** delivery, and the consensus `precheck_broadcast` parses the same `extra` with `CO_TRY` (`private-overlay.cpp`, `block-sync-overlay.cpp` precheck handlers), so a broadcast with unparsable `extra` is dropped before `on_overlay_broadcast` ever runs. The remaining `.move_as_ok()` calls on DB-loaded data (`db.cpp`, `candidate-resolver.cpp`, `collator-producer.cpp`, `block-producer.cpp`, `state-resolver.cpp`) read the node's own local database — attacker control there requires prior host/file control, excluded.

### 5. Other third-party-audit findings re-checked against this commit — all excluded

- **Finding 3 (empty `ConflictingCandidateAndCertificate`, no evidence for slashing):** `simplex/misbehavior.h:26-35` still stores no evidence, and all four `pool.cpp` call sites still pass commented-out arguments. This is the MisbehaviorProof/evidentiary gap the README **explicitly excludes**.
- **Finding 4 (three `FIXME: Report misbehavior` sites silently drop leader misbehavior):** still present in `consensus.cpp` (parent slot ≥ own slot; second candidate for a slot; rejected candidate). A Byzantine leader degrading liveness without on-chain consequence is validator-initiated; no single-message halt or unauthorized state change follows.
- **Finding 5 (two-step broadcast dedup after rebroadcast):** overlay-level replay amplification. In the current code the simple path already checks `is_delivered` before precheck/rebroadcast (`broadcast-twostep.cpp`), and in any case replay amplification is OOM/DDoS/resource exhaustion, explicitly excluded — and the overlay transport itself is outside the listed Simplex file set.

## Limitations

- **Static analysis only.** No dynamic testing, fuzzing, or local-network reproduction was performed, and no build was attempted. A build is infeasible in this environment as configured: the sparse checkout has **no submodules** (`git submodule status` shows all submodules uninitialized, including tdutils and all third-party libs), the VM has ~6 GB RAM / ~1.5 shared CPUs, and a full TON build (or even the `test-consensus` target the prior audit used) would require fetching the full source + submodules and a Clang 18+ toolchain. No build feasibility beyond that was established.
- **Generated TL code not reviewed.** `auto/tl/ton_api.hpp` (fetch/dispatch for `UnsignedVote`, `CandidateData`, etc.) is generated at build time and is absent from this checkout; the conclusion that `fetch_tl_object` rejects unknown TL constructors (observation: `Vote::from_tl`'s `*result`) rests on the standard TON TL-codegen behavior, not on a read of the exact generated file.
- **Residual uncertainty.** The null result is a statement about the code as reviewed, not a proof of absence. The largest residual uncertainty is the interaction between the pool's `skip_intervals_` bookkeeping and concurrent certificate arrival (the `lower_bound` invariant in `next_nonskipped_slot_after` was traced by hand through skip/finalize orderings and held in every ordering constructed, but it was not machine-checked) — and, in any case, skip/notar certificates are quorum-signed, so a defect there would fall in the excluded quorum class. Second is the exact behavior of `fetch_tl_object` on adversarial TL bytes (above).
- **No duplicate/known-report check against the bounty's private intake** was possible; only the public README exclusions, the repos' own comments, and the public Tesserae Ventures audit (2026-03-14) were consulted. Observation 1 is already publicly reported, which is itself a duplicate risk for that family.
- **Out-of-scope code was not audited:** block validation internals (`validator/impl/`, collation), the overlay layer beyond the precheck/delivery/membership paths cited, ADNL, RLDP, DHT, and the validator manager. A candidate that passes Simplex signature checks but crashes *block validation* would live in that unaudited code — but reaching it still requires a leader/collator signature, i.e. validator-side initiation.

## Recommendation

**Do not submit anything from this audit.** There is no candidate that plausibly meets the CRITICAL bar (single remote consensus message from an unprivileged sender halting a node/network or manipulating state/funds) in the reviewed revision.

If the user wants to keep hunting in TON Core, the higher-yield next targets are outside this file set: the block-validation/collation path that a leader-signed candidate flows into, and the overlay/ADNL membership and broadcast paths (noting the program excludes RLDP/DHT and all DDoS, so any finding there must survive those exclusions). Within Simplex itself, the only honest follow-up is the observation-1 race family — and it is already publicly reported and fails the program's single-remote-trigger requirement, so it should not be pursued as a submission.
