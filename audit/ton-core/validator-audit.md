# TON Validator Node — Bug Bounty Audit (block/transaction validation & cell parsing)

**Date:** 2026-11-11 (WIB)
**Program:** TON Security Bug Bounty (README at `~/workspace/ton-bug-bounty/README.md`; self-check skill at `~/workspace/ton-bug-bounty/skills/bug-bounty-self-check.md`)
**Method:** Read-only static analysis of public source code, cloned locally. No exploit traffic, no state-changing tests against public mainnet/testnet nodes, public RPC/lite servers, or any live network. No submission was made and the bounty bot was not contacted.
**Scope bar applied:** Only CRITICAL vulnerabilities qualify — (1) unauthorized manipulation of blockchain state or funds, (2) network halts, (3) node halts triggered by a **single** request from an **unprivileged** attacker (no validator key, no leaked key, no prior host/file control, no faulty-quorum/majority precondition).

## Verdict: NO QUALIFYING FINDING

No candidate was found that plausibly meets the program's critical bar. The one attack surface an unprivileged attacker can actually reach with a single request — an **inbound external message** — is defended in depth at every layer (size/depth limits, error-returning BoC deserialization, quiet TLB unpacking, VM errors caught and converted to rejections, big-integer fee/gas math). Every `CHECK()`/abort-class site found in scope is either provably unreachable from attacker-controlled data, guarded by a preceding check/throw, or reachable only via quorum-signed blocks — and `CHECK()` fail-stop under a faulty quorum is **explicitly excluded** by the README as intentional behavior. **Submit nothing from this audit.**

## Threat model applied (what "single remote block/message/transaction" can mean here)

Three input classes were distinguished, because only one is unprivileged:

1. **Inbound external message (unprivileged).** Any user can submit an external message (via lite-server `sendMessage`, or gossip) addressed to any account. This is the only single-request surface reachable without any validator privilege. The path is: `ExtMessageQ::create_ext_message` (BoC deserialize + TLB validation) → `ExtMessageChecker::check_inner` (state lookup, account unpack, `run_message_on_account` → `Transaction::unpack_input_msg` / storage / compute / VM) → mempool → collator re-execution → block validation. A crash anywhere on this path would be a qualifying single-request node halt — **none was found**.
2. **Candidate block / block proof from a peer (validator-gated).** `AcceptBlockQuery::precheck_header` runs TLB unpacking on the block before signatures are verified (step 7, `accept-block.cpp:251`), which initially looked promising. But (a) all unpacking there goes through `tlb::unpack_cell`, which uses `load_cell_slice_quiet` (`crypto/tl/tlblib.hpp:428-450`) — pruned/special/malformed cells return `false`, they do not throw; (b) `unpack_block_prev_blk_try` wraps its work in `try/catch (VmError, VmVirtError)` (`crypto/block/block.cpp:2044-2055`); (c) block bytes first pass through `BlockQ::init` (`validator/impl/block.cpp:37-69`: lazy BoC creation, root-count check, root-hash check, all error-returning). And a block that survives precheck still needs quorum signatures before it is applied or validated — a crash *after* that point requires a faulty quorum, which the README explicitly excludes as intentional fail-stop. The same gating applies to `validate-query.cpp` (full block validation runs only on signature-accepted blocks) and to `top-shard-descr.cpp` / `shard.cpp` (descriptions and proofs from other validators).
3. **Validator/config-controlled data (excluded).** Config parameters, validator sets, gas prices, `lt_align` (a `constexpr`, `mc-config.h:605`), collator options, and `rand_seed` are operator/validator-voted inputs. `CHECK()`s on those invariants (e.g. `mc-config.cpp:1927,2009`, `validator-set.cpp:61`, `shard.cpp:361,487`) are out of scope by the README's exclusions (validator-initiated attacks, trusted operator inputs, faulty-quorum fail-stop).

## What was verified (defense-in-depth on the unprivileged path)

- **BoC deserialization** (`crypto/vm/boc.cpp:808-918`, `772-805`, `37-88`): header parsed with bounds checks, CRC32C verified when present, root indices range-checked, per-cell `CellSerializationInfo::init` validates `refs_cnt`, `data_len`, offsets; `deserialize_cell` rejects forward references and out-of-range refs. `DataCell::create`'s `CHECK(bit_length >= 0 && data.size()*8 >= bit_length)` (`DataCell.cpp:349`) is provably unreachable from BoC input: `get_bits` derives `bits ≤ (data_len-1)*8+7 < data_len*8` and `data_with_bits` implies `data_len ≥ 1`.
- **External-message admission** (`external-message.cpp:96-150`): max-size and max-depth limits enforced before parsing; root must be a single level-0 cell; TLB `t_Message_Any` + hand-written `t_Message` validation; destination must parse as a valid std address. `get_ext_in_msg_hash_norm` builds a small fixed-shape cell (bounded bits), so its `cb.finalize()->get_hash()` cannot hit a null finalize.
- **Transaction unpacking** (`transaction.cpp:876-1055`): every parse step returns `false` on failure; external-message forwarding fees computed with `uint128` (`MsgPrices::compute_fwd_fees`, `compute_fwd_ihr_fees`) and `RefInt256` big-int arithmetic throughout — no `uint64` overflow in gas/fee/balance math. `gas_bought_for` inverts the price function with big ints; `to_long()` saturates to a sentinel (`bigint.hpp:1072-1090`), it does not throw.
- **Storage/compute/action phases**: `FAIL_UNLESS` is a return-false macro (`transaction.cpp:30-45`), not an abort — including `FAIL_UNLESS(sgn(balance.grams) >= 0)` after gas-fee deduction, which is in any case unreachable by construction (gas bought ≤ balance). VM execution goes through `vm.run()`, which converts `VmError` to an exit code; the checker re-runs a rejected message with logging and returns a `Status`, never propagating an exception. `CombineError` throws from TLB dict-combining are caught inside `Dictionary::combine_with` (`crypto/vm/dict.cpp:1812,2264,2550`) and surface as `false`.
- **Cell parsing**: `CellSlice::load` throws `VmError`/`VmVirtError` only on pruned/special/library cells, and every production caller on attacker-adjacent data either uses the quiet variant or is wrapped in `try/catch (VmError, VmVirtError)` (`check-proof.cpp` validator + `crypto/block`, `accept-block.cpp:743`, `proof.cpp`, `top-shard-descr.cpp`, `transaction.cpp:1253,2412`). `CellSlice::fetch_*` return EOF sentinels instead of throwing; `prefetch_ref` returns a null `Ref` out of range.
- **Proof verification** (`crypto/block/check-proof.cpp`, `validator/impl/check-proof.cpp`, `validator/impl/proof.cpp`): Merkle-proof virtualization happens before hash comparison, but `MerkleProof::virtualize`/`unpack_proof` return errors on null/non-MerkleProof/level≠0 roots, and all callers catch `VmError`/`VmVirtError` (one site also has `catch (...)`). `check_block_header_proof`'s `upd_cs.prefetch_ref(1)` is guarded by `size_ext() == 0x20228` (552 bits, exactly 2 refs). `BlockProofLink::validate` checks root hashes before unpacking headers.
- **All `std::optional::value()` sites checked** (`collator.cpp:110,710,1406,2828,3011-3033,3471,4526,4635,5944,6899`; `validate-query.cpp:275,2542,2560,3703,4329-4345`; `ext-message-pool.cpp:420`) are preceded by an explicit presence check on the same optional.
- **Output-queue merger** (`output-queue-merger.cpp`): fork/leaf handling validates `size_ext() == 0x20000` before `prefetch_ref`; `get_node_lt` handles null nodes; heap access is guarded by `empty()` checks; `msg_list.at(pos)` is bounded by `next()`/`load()` logic.

## Most interesting non-qualifying observations (NOT reportable — do not submit)

1. **`MerkleProofCombineFast::merge`: `CHECK(csa.size_refs() != 0)` (`MerkleProof.cpp:226`), plus a latent null-deref shape.** `merge` recurses with `csb.prefetch_ref(i)` for `i < csa.size_refs()`; if `b` had fewer refs than `a`, the recursive call would dereference a null `Ref` at `b->get_hash()`. Not reportable: (a) `combine_fast` has **no production caller** — only `crypto/test/test-db.cpp`; the production combiner is `MerkleProof::combine`, used in `collator.cpp:6547` on proofs the validator **generated itself** from its own state roots; (b) `run_raw` first requires `a_->get_hash(0) == b_->get_hash(0)`, and equal cell hashes imply equal structure (ref count included in the hash preimage), so a ref-count mismatch needs a SHA-256 second preimage, not a crafted input.
2. **`MerkleProofCombine` / `MerkleUpdate::get_any_cell` `UNREACHABLE()` (`MerkleProof.cpp:288`, `MerkleUpdate.cpp:382`).** Both fire only if a `cells_` entry exists with neither a real cell nor a pruned cell. `dfs()` always populates one of the two for every visited hash, and lookups in `do_create_A` are on hashes visited by `dfs` at the matching depth. Inputs are validator-generated proofs (combine) or quorum-signed block state updates (MerkleUpdate). Not attacker-reachable; also no proof that the invariant can actually be violated.
3. **`CellSlice::load` pruned-branch `CHECK(loaded_cell.effective_level >= loaded_cell.data_cell->get_level())` (`CellSlice.cpp:1129`).** Provably unreachable: the same condition is tested two branches earlier and throws `VmVirtError{1}` when violated (`CellSlice.cpp:1091-1095`). Redundant defense, not a bug.
4. **`CellString::load` / `CellText::load` `CHECK(to.offs == (int)size)` (`CellString.cpp:79,196`).** Two-pass deterministic invariant: the first pass sums the exact slice sizes the second pass concatenates; nothing mutates the chain between passes. `CellString::load` also performs no per-pass size cap, but total size is bounded by the message's cell/bit limits, and resource-exhaustion impacts are excluded anyway. Reachable only through TVM string opcodes on contract-controlled data, inside gas-limited VM execution.
5. **`ExtMessagePool::cleanup_expired_messages` `CHECK(it != ext_messages_hashes_.end())` (`ext-message-pool.cpp:361`).** Pure internal bookkeeping invariant: a message enters the expiry list only via `link_message` after being inserted into `ext_messages_hashes_`, and every erase path unlinks first. No attacker-controlled input can desynchronize the two structures.
6. **`AcceptBlockQuery` / `CheckProof` `CHECK`s (`accept-block.cpp:362,364,552,564,592,607,665,671,754,770,784,831,848`; `check-proof.cpp:197,278,323,332-367,390,456,463,468`).** All operate on internal query state or on blocks/proofs that have already passed root-hash and (for the validation phase) quorum-signature checks. A failure here requires a faulty quorum or a validator-side bug — both excluded.
7. **`Transaction::prepare_compute_phase` `FAIL_UNLESS(sgn(balance.grams) >= 0)` (`transaction.cpp:1835`).** Return-false, not abort; and unreachable by construction as analyzed above.
8. **`TotalValidatorSet::at_weight` `CHECK(weight_pos < total_weight)` (`mc-config.cpp:1927`) and the `CHECK(total_wt > 0)` / hole-invariant CHECKs (`mc-config.cpp:2009-2025`).** Validator-set selection from validator-voted config; `p` is `next_ranged(total_wt)` adjusted past removed-weight holes, so `p < total_weight` is maintained by construction. Config-controlled, not attacker-controlled.
9. **`BagOfCells::get_idx_entry_raw` `custom_index.at(index)` (`boc.cpp:949`)** can throw `std::out_of_range` in principle, but `get_cell_slice` bounds the index against `cell_count` first and `deserialize` iterates `i < cell_count`; no caller passes an out-of-range index. No unguarded-throw path was found on any attacker-reachable input.

## Limitations

- **Static analysis only.** No build, fuzzing, formal verification, or local-emulator execution was performed. No build was attempted: no candidate finding emerged that required one to verify, and a full TON build on this VM (~6 GB RAM, ~1.5 shared CPUs) would be slow and OOM-prone; build feasibility is recorded as **not attempted, not needed for this verdict**.
- **Coverage gaps.** `validate-query.cpp` (7,936 lines) and `collator.cpp` (~7,000 lines) were reviewed by targeted grep of all `CHECK`/`.value()`/division/exception sites plus full reads of the highest-risk sections (external-message import, gas/fee math, action phase), not line-by-line. TVM execution internals (`crypto/vm/` except `cells/` and `boc.cpp`) were outside the assigned file list; a `CHECK()` abort inside a TVM opcode implementation, reachable from arbitrary contract code during collation/validation, would be the highest-value remaining surface and was **not** covered here.
- **Residual uncertainty.** The null result is a statement about the code as reviewed, not a proof of absence. The largest residual uncertainties are (a) the two large files above, (b) TVM opcode internals, and (c) the td actor framework's uncaught-exception behavior (tdutils not in the sparse checkout) — relevant only if an unguarded throw exists on an attacker path, of which none was found.
- **No duplicate/known-report check against the bounty program's private intake** was possible; only the public README exclusions were applied. A finding identical to an already-submitted report would be a duplicate even if technically valid.

## Recommendation

**Do not submit anything from this audit.** There is no candidate that plausibly meets the CRITICAL bar (unauthorized state/fund manipulation, network halt, or single-request node halt by an unprivileged attacker) in the reviewed revision.

If the user wants to keep hunting in TON Core, the higher-yield next targets (in order) would be: (1) TVM opcode implementations in `crypto/vm/` (`cellops`, `arithops`, `contops`, `dict` handling of attacker-crafted contract code during collation) — the one large in-scope surface this audit did not cover; (2) a dynamic test of the external-message path with a local node build and a fuzzer over `create_ext_message` + `run_message_on_account`, which would convert this audit's static "guarded" claims into executed evidence; (3) Simplex consensus (`validator/` simplex code, excluded here only by the assigned file list) — noting `MisbehaviorProof` absence itself is excluded.
