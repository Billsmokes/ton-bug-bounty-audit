# TON Core — Full Node Network Surface Audit (ADNL / Overlay / Block & State Download)

**Date:** 2026-11-11 (WIB)
**Program:** TON Security Bug Bounty (README at `~/workspace/ton-bug-bounty/README.md`; self-check skill at `~/workspace/ton-bug-bounty/skills/bug-bounty-self-check.md`)
**Method:** Read-only static analysis of public source code, cloned locally. No exploit traffic, no state-changing tests against public mainnet/testnet nodes, public RPC/lite servers, real deployed contracts, or third-party services. No submission was made and the bounty bot was not contacted.
**Scope bar applied:** Only CRITICAL vulnerabilities qualify — a **single remote request/packet/message** from an **unprivileged** attacker (no validator key, no leaked ADNL/wallet/control key, no prior host/file control, no majority-quorum) that (1) unauthorisedly manipulates blockchain state or funds, (2) halts the network, or (3) halts a node. All README exclusions applied (OOM/DDoS/resource exhaustion, validator-initiated attacks, quorum-signed malformed blocks / fail-stop CHECK() under a faulty quorum, public-overlay Sybil, local-tool/debug-only failures, timestamp overflows, unsynchronised lite-server issues, control-interface misconfiguration, Simplex MisbehaviorProof absence). Excluded components (Catchain 1.0, Tonlib, RLDP 1/2, DHT Node, lite-client, Libemulator, compilers, explorer, TON Storage, Payment Channels, TON Proxy, https-proxy, rldp-http-proxy, liteserver) were not audited as targets.

## Verdict: NO QUALIFYING FINDING

No candidate was found that plausibly meets the program's critical bar. Across the whole reviewed surface, the pattern is consistent: remote-supplied data is either (a) signature-checked before use (ADNL packets, overlay broadcasts — the claimed source key must sign the exact payload), (b) hash-bound to an already-validated identifier before it is trusted (downloaded block data vs `file_hash`, downloaded state vs `root_hash` from a validator-set-validated proof, split-state parts vs hashes in a hash-validated header, archive import vs file hashes + proof checks), or (c) rejected with a `Status::Error` / dropped packet instead of reaching an unchecked assumption. Every `CHECK()` / `LOG(FATAL)` / `UNREACHABLE()` in the reviewed files was traced to a trigger condition and none was reachable by a single unauthenticated remote packet/message. **Submit nothing from this audit.**

This is a valid result, not a failure: this is mature, heavily exercised transport code, and the most recent broadcast layer (Plumtree) in particular is visibly hardened — duplicate checks are re-done after every `co_await`, size/signature/date checks precede decoding, and delivery only happens after a SHA-256 match.

## What was verified per area

### A. ADNL transport — signature-gated before any dispatch

- **Packet entry (`adnl-peer-table.cpp:receive_packet`, `adnl-local-id.cpp:receive_coro`).** A UDP datagram is routed only by its first 32 bytes (destination local-id short / channel id); anything to an unknown destination is dropped. Decryption is via the keyring for the destination local id; the TL parse (`adnl_packetContents`) and `AdnlPacket::create` run `run_basic_checks()` (unknown flags, both one-message and multi-message flags, one-message count ≠ 1, from/from-short mismatch, empty address lists all rejected with `protoviolation`).
- **Per-peer authentication (`adnl-peer.cpp:receive_packet`, `receive_packet_checked`).** Every non-channel packet is signature-checked with the peer's encryptor (`encryptor_->check_signature(packet.to_sign(), packet.signature())`) before `receive_packet_checked`. An attacker can only send packets signed by a key they own — i.e. as their own ADNL identity, against their own peer-pair state. Sequence numbers are replay-guarded (`received_packet`/`add_received_packet` mask), `confirm_seqno` above `out_seqno_` is dropped, reinit dates in the future (> now + 60 s) or older than the current one are dropped, and a reinit only resets *that* peer-pair's seqnos/channels.
- **Huge-message reassembly (`adnl-peer.cpp:process_message(AdnlMessagePart)`).** `total_size` is rejected if `> huge_packet_max_size()`; zero hash rejected; a part with `offset != 0` for a new hash is dropped; `data.size() + offset > size` is dropped; size inconsistency across parts is dropped; the assembled buffer is SHA-256-checked against the claimed hash before TL parsing, and a parse failure is dropped. The `int32 → uint32` cast of `total_size_`/`offset_` in `adnl-message.cpp:47-48` is safe here because the `> huge_packet_max_size()` check runs on the cast value (a negative int32 becomes a huge uint32 and is rejected).
- **Channel creation (`create_channel` / `ConfirmChannel`).** `CHECK(!channel_ready_)` after the reset branch is safe: `channel_ready_` is set false in the same reset branch, and is only set true after a successful channel creation + confirm with the matching peer key. `AdnlChannel::decrypt` returns errors via promise (bad TL / bad packet / wrong `from_short`) instead of crashing.
- **Ext TCP server (`adnl-ext-server.cpp`, `adnl-ext-connection.cpp`).** Init packet must be ≥ 32 bytes; length field is bounded (`64 ≤ len ≤ 1<<24`); packet SHA-256 is verified before dispatch; `tcp_authentificate` requires a 1–512-byte nonce, rejects duplicates, and `tcp_authentificationComplete` requires an Ed25519 key and a valid signature over the nonce before `remote_id_` is set. `process_packet` only forwards a well-formed `adnl_message_query` to `deliver_query`.
- **Peer-table CHECKs.** `CHECK(it2 != local_ids_.end())` in `add_peer` (line 183) and `LOG_CHECK(it != local_ids_.end())` in `subscribe` (line 292) / line 672 are reached only from local code paths (adding a peer for a known local id; subscribing a local id) — no remote packet supplies the local id used there (inbound packets to an unknown local id are dropped in `receive_packet`). The `CHECK(pending_ > 0)` pair in the stats callbacks (lines 513, 577) is a locally balanced inc/dec counter in a stats actor, not remote-reachable. `CHECK(id.pubkey().is_ed25519())` in `add_id_ex` guards a local operator call.

### B. Overlay broadcasts — signature + size + hash before decode/delivery

- **Simple (`broadcast-simple.cpp`).** `check_date` (±20 s), source-eligibility, rate-limiter precheck, then signature verification over `(broadcast_hash, date)` before `register_broadcast` / delivery / rebroadcast. Duplicates are dropped via `has()` / `is_delivered()`.
- **FEC (`broadcast-fec.cpp`).** Full parts: `check_date`, `FecType::create`, `fec_type.size() == data_size_` match, `seqno < symbols_count*2+4`, certificate creation, then `process()` → `run_checks` (signature over `(part_hash, date)` + source eligibility + duplicate-part check) → `run()` → `add_part` → `finish()` only decodes when enough symbols are present and **SHA-256 of the decoded data must equal `data_hash_`** before delivery. Short parts are only accepted for an already-finished broadcast, with the part hash re-checked against the locally re-generated symbol. `CHECK(received_parts_.insert(seqno).second)` (`add_received_part`, line 147) is unreachable from a remote duplicate because both call paths (`process` full and short) run `run_checks` first, which rejects an already-received seqno — and the local signed-send path goes through the same `process()`. `CHECK(decoder_)` in `finish()` (line 86) and `CHECK(encoder_ != nullptr)` (line 95) hold because `decoder_` is created by `init_fec_type()` before any part is processed and is only cleared inside `finish()` after success, and `finish()` is only called while `!ready_`.
- **Two-step (`broadcast-twostep.cpp`).** Simple: date, duplicate, source eligibility, limiter precheck, `precheck_broadcast` (twice, with a re-check of date/duplicates after the second await), signature, limiter registration, then delivery. FEC: `part_size >= data_size` rejected; `seqno >= persistent_node_count()` rejected; source eligibility + limiter precheck + signature precede `Decoder::create`; duplicates re-checked after the await; decoded data is SHA-256-checked against `data_hash_` before delivery. A negative `int32 data_size_` becomes a huge `uint32` and is rejected by `check_rules` (authorised-key cap or `max_unath_size_`, both ≤ 16 MiB in the validator overlays) via `check_source_eligible` — see observation 1 for the residual caveat.
- **Plumtree (`broadcast-plumtree.cpp`, 2,119 lines).** The most hardened path reviewed: `validate_control_fields` (zero id, `tree_index >= tree_slots_`, simple/FEC tree-index correspondence), `check_timestamp`, `full_data_size == 0 || > max_fec_broadcast_size (16 MiB)` rejected, `part_size == expected_part_size` (computed from `k_`), eager-peer-only origin check (or exact repair-key match for repair responses), broadcast-id collision checks, source eligibility, limiter precheck, signature verification — and after each `co_await precheck_broadcast` the duplicate/state/collision checks are **re-done** before state is created or a part is stored. Decoding only happens via `add_decoder_part_and_decode`, which skips already-seen `part_index` values, and delivery requires the decoded SHA-256 to match `full_data_hash`. IHAVE handling caps repair targets, defers signature checks only for canonical Ed25519 signatures of fixed size, and verifies deferred signatures before sending a repair request. `CHECK(active_repair_queries_ > 0)` in `repair_query_finished` (line 1745) is paired with the increment in `send_repair_requests` and is invoked only by the local query-completion callback (`OverlayImpl::receive_plumtree_repair_response`, `overlay.cpp:904`) — a remote peer cannot invoke it. `CHECK(it != eager_peer_refcnt_.end())` / `CHECK(it->second > 0)` in `remove_eager_peer_ref` (lines 529–530) are safe because `remove_eager` only decrements when `slot.eager.erase(peer) > 0`, and every eager insertion goes through `add_eager_peer_ref`.
- **Overlay manager / dispatch (`overlay-manager.cpp`, `overlay.cpp`).** `receive_message` / `receive_query` parse only the TL prefix (`overlay_message[WithExtra]` / `overlay_query[WithExtra]`) and return errors on parse failure; unknown overlay/local-id is buffered (bounded by configured limits) or rejected — no crash path. `OverlayImpl::receive_message` falls back to the application callback for non-broadcast messages (block-candidate / block broadcasts go through `deserialize_block_broadcast` — see §C). `check_src_peer`'s `CHECK(P->is_permanent_member() || !cert.empty())` (overlay-peers.cpp:727) is safe: `validate_peer_certificate` has already returned OK, which for a non-persistent, non-public node requires a non-empty certificate. `OverlayNode::certificate()` never returns null (returns `&empty_certificate_` when unset), so the `*node.certificate()` dereference in `add_peer` (line 239) cannot null-deref. Peer-list `CHECK(deleted)` sites in `del_from_neighbour_list` are guarded by `is_neighbour()` / membership tests.
- **Overlay size gates.** `OverlayPrivacyRules::check_rules` forbids unauthorised broadcasts above `max_unath_size_`, forbids AnySender-flagged unauthorised broadcasts, and caps authorised senders at their registered size; `check_source_eligible` additionally forbids `size == 0`.

### C. Block / proof / state download — hash-then-trust at every step

- **`validator/full-node-serializer.cpp`** (the funnel for all of §C): `deserialize_block_full` / `deserialize_block_broadcast` return `Status::Error` on LZ4 decompression failure (bounded by `max_decompressed_data_size`), on BoC deserialisation failure, and on wrong root counts; the V2 variants additionally require a level-0 root. `extract_prev_blocks_from_proof` deserialises the proof BoC, unpacks `BlockProof`, requires `proof_blk_id == block_id`, virtualises the Merkle proof, and requires 1–2 previous blocks. `need_state_for_decompression` returns true only for the CompressedV2 variants, so the `UNREACHABLE()` fallback in `DownloadBlockNew::got_data` and the `CHECK(obj->get_id() == tonNode_dataFullCompressedV2::ID)` in `DownloadNextBlocks::process_block` are unreachable for other variants.
- **`DownloadBlockNew`**: after deserialisation, `id != block_id_` and `sha256(block_data) != id.file_hash` are rejected, and the proof is validated (`validate_block_proof` / `validate_block_proof_link`) before `finish_query`. A bad proof aborts the query; it does not crash the node.
- **`DownloadProof` / `GetNextKeyBlocks`**: TL parse errors abort the query; a partial proof when not allowed is rejected; `GetNextKeyBlocks::got_next_block_handle` checks `handle->is_key_block()` after `CHECK(handle->inited_is_key_block())` — the handle comes from `get_block_handle` *after* `validate_block_proof_rel` succeeded, so the CHECK is on locally-established state, not on remote input. `R.ensure()` sites in these files are on `get_block_handle(..., true)` (create-if-missing) or post-validation results; a failure there would require a local DB failure, not a remote packet.
- **`DownloadNextBlocks`**: `blocks_.size() > MAX_BLOCKS` and empty-block entries are rejected; each block is hash-checked and `validate_block_is_next_proof` is awaited before the handle advances.
- **`DownloadState` (net)**: state is fetched in 2 MiB slices (`part_size = 1 << 21`, answer capped at `part_size + 1024`); the last part is detected by a short read; the reassembled buffer's size is `sum_` of the received parts and `CHECK(!S.size())` (line 256) holds by construction (each part is copied exactly once). The downloaded state itself is **not** trusted here — it is validated downstream (`create_shard_state` + root-hash check + `validate_deep()` in `DownloadShardState::downloaded_shard_state`).
- **`DownloadArchiveSlice`**: slices are written to a temp file; the file is only used after archive import, which verifies per-block SHA-256 file hashes and proofs (`validator/import-db-slice.cpp:232,509`, `check_masterchain_block`, `run_check_proof_query` / `run_check_proof_link_query`).
- **`DownloadShardState` (`validator/downloaders/download-state.cpp`)**: zero states are SHA-256-checked against `block_id_.file_hash` before `create_shard_state`; unsplit states are root-hash-checked against `handle_->state()` and `validate_deep()`-checked; split-state headers are Merkle-proof-virtualised and hash-checked against `handle_->state()` (`get_effective_shards_from_header`), each downloaded part is SHA-256-checked against the hash listed in that validated header, and the final merged root is checked against `handle_->state()` again (`CHECK(state_->root_hash() == handle_->state())`, line 404) — a mismatch fails the download, it does not corrupt state. See observation 3 for the `merge()` FATAL analysis.
- **`WaitBlockData` / `WaitBlockState` / `WaitBlockStateMerge`**: `loaded_data` goes through `create_block` (which validates the block root against the id); proof-link generation/validation precedes `set_block_data`; `CHECK(sha256 == file_hash)` in `got_static_file` (wait-block-data.cpp:249) is on a **local static file** from disk, not on remote data; `CHECK(handle_->received())` in `finish_query` is on locally-set handle state after `set_block_data` succeeds.

### D. DB — remote data only arrives after validation

- **`celldb.cpp`**: the `MergeOperatorAddCellRefcnt::FullMergeV2` `CHECK(merge_in.existing_value)` / `CHECK(operand_list.size() >= 1)` operate on RocksDB merge operands written by the node's own validated state/block writes; `validate_meta`'s `obj.ensure()` / `LOG(FATAL)` (line 158) runs on local DB metadata at startup. No remote packet writes directly to celldb.
- **`archive-manager.cpp` / `rootdb.cpp`**: the `CHECK(v.move_as_ok() == GetStatus::Ok)` / `CHECK(it != m.end())` sites are on local RocksDB index reads for package descriptors created by the node itself; remote archive data reaches the archive only through the verified import path (§C).
- **`validator-engine.cpp` (full-node path only)**: full-node configuration is operator-supplied (config file / control interface — excluded as a target); the `CHECK`s found are on local startup state (`CHECK(!peer_table.empty())`, `CHECK(!keyring_.empty())`, `CHECK(keys_.count(id) > 0)`), local counters (`CHECK(pending_ > 0)` in control-query fan-out), or locally computed slices (export-private-keys length accounting, `CHECK(slice.size() >= size + 4)` / `CHECK(slice.size() == 32)`, where `data_size` is computed from the locally enumerated keys). The `UNREACHABLE()` at line 6174 is in a local `switch (iter)` over a 0–2 loop index. Control-query handlers require control-interface permissions and are excluded by the program.

## Most interesting non-qualifying observations (NOT reportable — do not submit)

1. **Twostep FEC has no explicit `data_size <= max_fec_broadcast_size` check before `Decoder::create` (broadcast-twostep.cpp: ~380–430).** The bound is enforced indirectly: `check_source_eligible` → `check_rules` rejects any `data_size` above the authorised-key cap or `max_unath_size_` (≤ 16 MiB on validator overlays), `precheck_new_broadcast(data_size)` runs the size rate limiter first, and a negative `int32 data_size_` becomes a huge `uint32` that `check_rules` rejects. So a single packet cannot reach the decoder with an unbounded size through this path. Residual: the RaptorQ decoder's internal allocation behaviour for a max-size (16 MiB, small-symbol) parameter set could not be verified locally because the `td/fec` submodule is not checked out — and any effect there would be resource exhaustion, which the program excludes. Not reportable.
2. **Unbounded accumulation in state/archive downloads (validator/net/download-state.cpp, download-archive-slice.cpp).** A malicious peer that keeps answering full 2 MiB state slices / full archive slices can make the node keep appending parts / growing a temp file indefinitely (there is no total-size cap enforced against `total_size_` in the part loop, and no cap on the archive file). This is resource exhaustion / DDoS, explicitly excluded by the program — and the peer is one the node itself chose to download from. Not reportable.
3. **`SplitStateDeserializer::merge()` can `LOG(FATAL)` on `VmError`/`VmVirtError` and `LOG_CHECK`s `combine_with` (validator/downloaders/download-state.cpp:107–124).** Not reachable from remote input as analysed: every part merged is SHA-256-checked against a hash in the split-state header, and the header itself is Merkle-proof-virtualised and hash-checked against `handle_->state()`, which comes from a validator-set-validated proof link — so the merged content is fixed by authenticated hashes, and disjoint prefix partitions cannot conflict. A `VmError` here would require an already-authenticated state to be internally inconsistent. Also note the loop bound `1 << (split_depth - shard_prefix_length)` (line 67, same loop in `validator/state-serializer.cpp:553`): `split_depth` comes from the persistent-state descriptor derived from validated masterchain state, not from a remote packet, so no attacker-controlled shift width. Not reportable.
4. **`WaitBlockData::got_static_file` `CHECK(sha256 == file_hash)` (wait-block-data.cpp:249).** The data is a local static file read from disk (`try_get_static_file`), not remote input. A corrupt local file is a local-host issue, excluded. Not reportable.
5. **`R.ensure()` before `move_as_ok()` on `get_block_handle` results** (download-block-new.cpp:82, get-next-key-blocks.cpp:177, download-state.cpp:163). These are on create-if-missing handle lookups or post-proof-validation lookups; tripping one would require a local DB/internal failure, not a remote packet. Not reportable.
6. **`AdnlLocalId::deliver` / `deliver_query` call `td::TlParser(s.as_slice()).fetch_int()` in a VLOG for unmatched custom messages/queries (adnl-local-id.cpp:105,127,130).** Reachable with an arbitrary (even empty) custom message after signature verification, so it was checked as a candidate. It could **not** be verified locally because the `td` submodule (`td/utils/tl_parsers.h`) is not in the sparse checkout and a fresh clone failed from this VM (see Limitations). It is **not** reported: `TlParser::fetch_int()` is used pervasively in logging paths across the codebase and is designed to return 0 / set an error flag on short input rather than abort; an empty custom message crashing the node would be a long-standing, trivially-triggered defect in heavily exercised code. Residual uncertainty is recorded honestly in Limitations.
7. **BroadcastFec `CHECK`s (`broadcast-fec.cpp:86,95,110,147`).** All are guarded by the duplicate-part and decoder-lifecycle checks described in §B; no remote single packet can reach them. The `CHECK(X.data.size() <= 1000)` / `CHECK(data.size() <= (1 << 27))` sites are on the **local sending** path (`BroadcastFecActor`), not on received data. Not reportable.
8. **Plumtree `repair_query_finished` `CHECK(active_repair_queries_ > 0)` (broadcast-plumtree.cpp:1745).** Increment and decrement are paired in local code (`send_repair_requests` → one promise → `receive_plumtree_repair_response`); a remote peer can only cause a repair query to be sent or answered, never invoke the decrement itself. Not reportable.
9. **Overlay `bcast_gc` `CHECK(delivered_broadcasts_.erase(Id))` / size-equality CHECK (overlay.cpp:683–685).** `register_delivered_broadcast` inserts into the set and the LRU together and only on a fresh insert, so the two structures cannot desync via remote broadcasts. Not reportable.
10. **`DownloadState` (net) `CHECK(!S.size())` after reassembly (download-state.cpp:256).** Holds by construction (`sum_` is the exact sum of the received part sizes). Not reportable.

## Limitations

- **Static analysis only.** No dynamic testing, fuzzing, differential testing, or local-node execution was performed. A single-packet crash that depends on a subtle interaction (e.g. RaptorQ decoder internals, `td::fec` / `td::raptorq` parameter handling) cannot be ruled out by reading the callers alone.
- **Build not attempted.** No candidate finding emerged that needed build verification, so no build was attempted (per task instructions). A full TON build on this VM (~6 GB RAM, ~1.5 shared CPUs) would be slow and at risk of OOM; this was not tested.
- **Submodules absent.** `td` (tdutils/tdactor/tdfec), `third-party/*` (incl. libraptorq), and the generated TL headers' upstream sources are not in the sparse checkout, and a fresh `git clone` of `ton-blockchain/td` failed from this VM (no network auth path). Consequences: (a) `TlParser::fetch_int()` behaviour on short input (observation 6) is unverified — believed safe, not proven; (b) `td::raptorq::Decoder::create` / `add_symbol` / `try_decode` bounds and failure modes (observations 1, §B) are unverified beyond their callers' checks; (c) `td::lz4_decompress` / `vm::boc_decompress` internals were reviewed only through their callers' size caps. The `crypto/vm` BoC code *is* in the checkout (`crypto/`) but was not line-audited in this task (it is one layer below the network surface; decompression bombs are in any case OOM-excluded).
- **Coverage gaps (by task scope).** Not audited as targets: the server side of full-node ADNL queries (`validator/full-node.cpp`, `validator/full-node-queries.*`, `validator/full-node-custom-overlays.cpp`, `validator/full-node-fast-sync-overlays.cpp` — only the shared `full-node-serializer.cpp` deserialisation they call was reviewed), block validation/collation (`validator/impl/*`), Simplex/Catchain, and `validator/db/archive-slice.cpp` internals (only the import-verification checks were confirmed). The largest residual uncertainty is the unverified `td/fec` decoder internals and the un-built, un-fuzzed packet parsers (ADNL/overlay TL parsing is generated code).
